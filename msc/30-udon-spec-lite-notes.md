## Why it's in the reading list — the pipeline (verbatim, `.int/vsect-requirements-on-lite.md`, 2026-09-30)

> *"The planned pipeline is spec-lite → a lite parser → vsect → aat-refactored. Later, spec-lite 0.1.1 is to be written *in* lite and managed *by* vsect. That makes the spec corpus, and vsect behind it, lite's first real customer."*

So: udon lite is the record/data substrate a verisectorium-managed AAT would be written and tooled in; vsect (the verisectorium tool) is the consumer that reads lite; AAT (then aat-refactored, now aat-v3) is the corpus vsect manages. **No vsect tool exists yet** (checked 2026-10-28: no binary on PATH, nothing under `~/src/arch/firmatum/utils/`; only the RC1 `lang/vsl.py` spike and `rc1-in-udon.ud` sketch). The descent recursive-descent generator (`udon/tools/descent/`, `udon/core/`) is lite's intended implementation route (adr `no-bespoke-parser`).

The nine vsect requirements on lite (that file) are worth re-reading before deciding v3's record format: robust fences (examples of reserved syntax only in fences); **status has no spelling in lite — projections live only in vsect output, never in files** (= RC1's "hand-set status inexpressible"); edges as plain names (`per: [implied-root]`) until `@` lands; source spans on every node as meta (for `revise` to know which named spans changed); append-safety; duplicate keys surface (collide); first-line greppability (`grep '^|decision\['`); `@` mid-token; stacked vs list.

## What lite is (`.int/README.md`, read whole)

- "The basic UDON subset" for data + document layout now; the dynamic parts (`!`, `@`, interpolation) reserved.
- **One contract: "Reserve, don't ignore"** — "Any document a lite parser accepts produces the same tree under every future full version of UDON." Reserved spellings are now *errors* that halt parsing (adr `reserved-is-an-error`).
- AST-centric (lite specified as the tree it produces); implied root; `|{…}` inline elements in; `<…>` explicit typed value carried as raw text (reopened 10-22: "still very cheap to change"); suffixes lose special status; tables deferred.
- Terminology: uses the address-theory vocabulary (`~/src/address-theory/def/`) where it applies; lite's own terms are records in `def/` with a generated lexicon; defined terms written «…» (SOP-store terms ⟦…⟧).

### Joseph verbatim, STEWARD-VERBATIM.md:698-800 (2026-10-08/09) — read whole; binding on v3's working rhythm

> So, you've been dutifully recording the discussion pieces and reasonings etc.-- the purpose of using a verisectorium format is the ease with which the spec can be mutated in these earlier stages especially-- reorganize-- write an alternate segment, etc. etc. Usually it doesn't do great for that when we are thinking of the segments as things that are too big-- not just a small rule with its reasons and rules that it impacts and rules that it derives from etc. All of our discussions so far-- each turn almost, could have been simply modifying the spec "cards" / segments themselves. It seems like, instead, you are queueing everything up for some massive final gathering?

> Here's the thing also-- no need to be holistic about the cards or outline! Just write cards for the tiny pieces as they come up-- then backfill later.

> Think of a traditional spec or ISO standard or something: 1. The such-and-such MUST such-and-such. <- one card. 2. The other thing MAY be this, or that. <- another card-- with some working notes and why it's important etc...

> As you start putting things in there-- you'll start (hopefully) instinctively using the frontmatter of each card to say which other rulings it depends on or assumes, for example, and the inverse-- which other rules are consequences of it-- with your "verbatim" quotes and reasoning as working notes in that very segment-- easy to find, easy to know what the impact of a change would be, etc.

> Isn't a card a decision already?

> partial orientation will also cause you to generalize incorrectly and assert new rules that should be obvious derivations of existing conventions and rules.

> fwiw, the 0.10 assertion that $main doesn't apply in braces was a (poorly reasoned) decision by an agent, not my decision (that I remember- if it was, it was poorly reasoned by me).

Implication for v3 (mine): a theory analog of "one MUST = one card" is roughly "one independently-failable claim (or definition, or choice) = one record" — matches RC1's grain invariant and the 09-29 "names for every assertion" proposal. And the working rhythm: each dialog turn with Joseph should *change records*, not queue findings for a later gathering.
